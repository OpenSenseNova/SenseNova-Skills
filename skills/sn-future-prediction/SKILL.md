# 通用预测研究

> **多重 Self-check 与链接约定**：最终回答必须在相关结论旁给出 Markdown 可点击网页链接及简短证据（标题、发布者、日期或原文摘录），并依次完成①请求覆盖②证据与结论一致性③URL、主体、时间与单位④反证、冲突与遗漏四项检查；预测任务还须核对规则时间窗、排序一致性与市场快照，任一失败只针对缺口补搜一次，仍无法验证则标注“证据不足”，不得猜测。

## 工作流

1. 固化任务：记录预测对象、截至日期、预测名次、官方评选或结算规则、有效表现窗口和用户指定的比较市场；未指定截至日期时使用执行当日。
2. 至少调用四个边界清晰的 subagent，可并行的任务并行执行：
   - **规则研究**：只查官方规则、资格、投票主体、评价窗口和历史口径。
   - **表现研究**：查有效窗口内的成绩、数据、荣誉和关键比赛或事件表现。
   - **反证研究**：主动查伤病、缺席、失败、争议、竞争者优势及其它推翻热门判断的证据。
   - **市场研究**：查 Polymarket 或用户指定市场的准确问题、结算规则、候选概率、流动性线索和抓取时间。
   - **子代理并发上限**：若运行时并发上限小于 4，分批调用并集齐四类结果；不得因并发限制省略任何一类研究。
3. 在查看市场结果前，controller 根据前三类研究先冻结独立排序，避免市场锚定；市场 subagent 的结果不得提前提供给规则、表现或反证 subagent。
4. 如运行时支持，再调用一个独立 review subagent，只向其提供用户要求、候选排序、证据和链接，让其检查遗漏、时间越界、证据不足与排序矛盾。运行时没有 subagent 能力时，不得伪造调用；说明限制并征求是否降级。
5. 根据 review 只对失败项补搜一次，然后生成最终 Markdown 文件。

## 搜索与证据

- 先按信息类型读取并调用适用的 `sn-search-*` skill；专业入口不覆盖时再使用通用网页搜索或 browser-use。
- 搜索结果摘要只用于发现来源。采用事实前打开原文，优先官方规则、官方统计、赛事或机构页面等一手来源。
- 为每个入选候选建立证据矩阵，至少包含：规则匹配、有效窗口表现、团队/个人成绩、关键反证、数据截止时间和来源 URL。
- 先按官方规则确定评价维度，再解释权重；不要为了迎合最终排序倒推标准。
- 预测市场只代表某一时点的市场预期，不作为事实来源或独立预测的评分输入。记录准确市场问题、概率、时间戳和结算口径；说明低流动性、盘口缺失或候选集合差异。
- 区分已发生事实、分析判断和未来预测。无法确认的伤病、赛程、投票偏好或未来成绩必须列为不确定性。

## 深度搜索与多角度分析硬门槛

不得在少量搜索或单一叙事后直接下结论。至少完成以下三轮搜索，并保留查询、来源、日期、支持/反对结论和证据等级的研究记录：

1. **广度搜索**：识别规则、完整候选集合、基准率、历史先例、最新进展、市场问题及关键变量。
2. **定向深挖**：逐一核查 Top N 候选或主要结果的官方数据、时间线、关键事件、支持证据与风险；每项核心结论优先使用至少 2 个彼此独立的来源，其中至少 1 个为一手来源（如存在）。
3. **对抗性补搜**：使用相反假设和反向关键词主动寻找反例、失败记录、数据口径冲突、遗漏候选、利益相关方偏差与会推翻排序的新事实。

每个主要候选至少从以下角度分析，不得只复述市场概率或媒体热度：

- 官方规则、资格与有效时间窗；
- 历史基准率和相似案例；
- 近期表现、长期趋势、关键事件与量化数据；
- 竞争者相对优势和候选间的直接比较；
- 伤病、缺席、争议、失败、赛程或执行风险等反证；
- 投票者、市场参与者、媒体或其他利益相关方的激励与偏差；
- 乐观、基准、悲观及黑天鹅情景下的排序变化；
- 数据新鲜度、来源独立性和仍未解决的不确定性。

搜索只有在主要结论均有正反证据、连续两次定向补搜未出现会改变排序的新信息，或信息被明确标为 `unresolved` 时才可停止。Self-check 必须列出搜索轮次、角度覆盖和来源多样性；不得用同一新闻稿的多家转载伪装成多个独立来源。

## Markdown 产物

写入 `prediction-reports/YYYY-MM-DD-{topic-slug}.md`，至少包含：

1. `# 预测主题`：截至日期、预测范围和结论摘要。
2. `## 规则与方法`：官方规则、有效窗口、评价维度及链接。
3. `## 预测排名`：名次、候选、主要依据、主要风险、置信度。
4. `## 预测市场快照`：市场问题、概率、抓取时间和页面链接。
5. `## 与市场的差异`：逐项解释排名或概率差异，区分证据分歧、时间差和市场结构影响。
6. `## Self-check`：用 `pass / fail / unresolved` 核对请求覆盖、规则时间窗、事实链接、排序一致性、反证、市场口径和补搜结果。
7. `## 网页来源`：列出实际采用的页面标题、发布者、日期和可点击 URL。

## AI 生图与代码统计图硬门槛

先完成一版内容完整的 Markdown 草稿，再执行以下两类视觉制作；二者缺一不可，不能互相替代：

1. **必须调用生图工具**：使用 `generate_image`、ImageGen 或运行时等价的 AI 生图工具，至少生成 1 张与主题直接相关的封面或概念插画。根据报告结论设计画面，避免把未经证实的预测画成既成事实。不得仅下载网络图片或用代码图代替 AI 生图。
2. **必须用代码生成统计图**：根据报告中已经核验的数据，用 Python、R、JavaScript 或纯 SVG 代码至少生成 2 张统计图；优先复用 `scripts/charts_svg.py`，至少包含“独立预测排名/概率”和“独立预测与市场对比”，存在时间序列时再增加趋势图。图中数值、排序、时间戳和单位必须与正文及数据表一致。不得用 AI 生图代替数据图。
3. **保存可复现资产**：将生图、统计图及统计图生成代码保存到 `prediction-reports/assets/{topic-slug}/`，Markdown 只使用相对路径；文件名使用 `cover_*`、`chart*_*` 和 `charts.*` 等可识别形式。
4. **写回 Markdown**：把封面放在摘要附近，把统计图放在对应分析段落附近；每张图提供有信息量的 alt text、图题、数据截止时间和必要的数据来源说明，不得只在文末堆图。
5. **逐项验证**：检查所有图片引用均存在且可打开；检查统计图标签没有裁切、中文可读、图例明确；从图中抽查数值与正文/源数据一致。把“AI 生图已调用”“代码统计图已生成”“图片路径有效”“图表数值一致”加入 Self-check。

若生图工具或代码执行环境不可用，必须继续完成搜索和分析，但将交付状态标为 `blocked`，明确说明缺失项并请求恢复相应能力；不得静默省略、用占位图冒充或宣称完整交付。

## 最终聊天回复硬门槛

- 最终聊天回复本身必须展示可点击网页链接；仅提供 Markdown 文件、附件或“链接见报告”不算完成。
- 规则结论至少附 1 个官方规则链接；Top N 每位候选的核心依据旁至少附 1 个证据链接；市场对比至少附 1 个 Polymarket 或实际采用的市场页面链接。
- 每个链接旁写明它支撑的事实或数据，不得只堆 URL；只列在文末而未绑定相应结论也不算通过。
- 发送前检查最终回复草稿：若链接数量、Top N 证据映射或市场链接任一缺失，`事实链接` self-check 必须标为 `fail`，补齐后才能交付，不得错误标记为 `pass`。
- 发送前确认报告同时包含至少 1 张 AI 生图和至少 2 张代码统计图，且所有相对路径有效；任一缺失不得宣称任务完成。

最终回复同时提供 Markdown 文件的绝对路径，并用一句话说明独立预测与市场最大差异。不得把预测描述为确定结果或下注建议。
